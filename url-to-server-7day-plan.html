Day 1 2.5 h

Big picture and URLs

Before you zoom into any single stop, see the whole trip. Today you build the mental map that every later day fills in.

1.1 The internet vs. the web, and the client–server model

The internet is the physical and logical network of cables, routers and protocols that moves data between machines. The web is one application that runs on top of it — pages linked by URLs, delivered over HTTP. Email, DNS and video calls are other applications on the same internet.

Almost every web interaction is client–server: your browser (the client) asks a question, a server answers it. The server is just a computer that stays on, listens on a port, and runs software built to answer that kind of question. A CDN edge node, a load balancer and an origin server are all "servers" playing different roles in the same conversation — you'll meet each on Day 5.

SEO angle: Googlebot is a client too. Everything that makes a page slow or unreachable for a human browser — DNS failures, connection timeouts, a server that's down — makes it slow or unreachable for Googlebot, and that shows up as crawl errors and crawl budget waste in Search Console.
  • Common mix-up: "the internet is down" when actually one website's server is down. The network layer and the one application are not the same thing.

1.2 Anatomy of a URL

Take https://www.example.com:443/blog/seo-guide?utm_source=news&page=2#intro apart:

  • Scheme — https. Tells the browser which protocol to speak, and implies the default port.
  • Host — www.example.com. The domain name the browser must resolve to an IP address.
  • Port — 443. Almost always implicit (80 for HTTP, 443 for HTTPS); rarely written out.
  • Path — /blog/seo-guide. Which resource on that server.
  • Query string — ?utm_source=news&page=2. Extra parameters; the server decides whether they change the response.
  • Fragment — #intro. Never sent to the server at all — resolved entirely inside the browser.
SEO angle: the fragment never reaching the server is exactly why URLs that differ only after # are the same URL to a crawler. Query strings, by contrast, can create infinite crawlable duplicates (faceted navigation, tracking parameters) — this is where canonical tags and parameter handling start.
  • Assuming a trailing slash, a fragment, or parameter order never matters for indexing — they can, depending on server and canonicalization setup.

1.3 The journey at a glance

Memorize this order — every later day expands one link in this chain:

  1. Browser parses the URL and checks its own caches (HSTS list, DNS cache, HTTP cache) for shortcuts.
  2. If needed, DNS resolves the host to an IP address.
  3. Browser opens a TCP connection to that IP on the right port.
  4. For HTTPS, browser and server perform a TLS handshake to encrypt the channel.
  5. Browser sends the HTTP request; the server (often via a CDN or reverse proxy) processes it.
  6. Server sends back headers, then the response body starts arriving — the byte stream downloads.
SEO angle: this exact order is what Chrome's Network → Timing tab shows for every request, and it's the order Google's own crawl-efficiency guidance follows. When someone says "TTFB is slow," they mean step 6 started late — but the cause can be anywhere in steps 1–5.

Day 2 2.5 h

IP addresses and domain names

Domains are the label; IP addresses are the destination. Today you learn what a name actually resolves to, and who's responsible for the name itself.

2.1 IPv4, IPv6, NAT and ports

An IPv4 address like 93.184.216.34 is four 8-bit numbers — about 4.3 billion possible addresses, long since exhausted for public use. IPv6 addresses like 2606:2800:220:1:248:1893:25c8:1946 use 128 bits, enough addresses that exhaustion isn't a practical concern. Most sites today answer on both; DevTools and dig will show you which.

NAT (Network Address Translation) is why your home network's many devices share one public IPv4 address — your router rewrites the packets. A port is a number (0–65535) that identifies which service on a given IP to talk to: 80 for HTTP, 443 for HTTPS, 22 for SSH. An IP without a port is like a building without an apartment number.

SEO angle: if your site resolves to different IPs for IPv4 vs IPv6 and only one is configured correctly (firewall, certificate, load balancer), some crawlers or users on that stack will fail silently while others succeed — a classic "works on my machine" crawl issue.

2.2 Domain names: registry, registrar, and DNS host

Three different roles, often confused:

  • Registry — the organization that runs a whole top-level domain (e.g. Verisign runs .com; a country's registry runs its ccTLD). They keep the master list of who owns what.
  • Registrar — the company you actually buy the domain from (Namecheap, GoDaddy, Cloudflare Registrar…), accredited by ICANN to sell registry names.
  • DNS host / nameserver provider — whoever actually answers DNS queries for your domain's records. Often the registrar by default, but frequently moved to a dedicated provider (Cloudflare, Route 53, your CDN) for speed and features.

These three can be three different companies at once, and that's normal — and exactly why "my DNS won't update" support tickets get confusing.

SEO angle: during a site migration, "update the DNS" can mean changing nameservers at the registrar (pointing to a new DNS host entirely) or just editing records at your existing DNS host — very different actions with very different propagation behavior. Knowing which layer you're changing prevents downtime.
  • Contacting the registrar to fix a DNS record that's actually managed elsewhere (or vice versa).

Day 3 3 h

How DNS resolves a name

The single most misunderstood step in the whole journey. Today you trace exactly who is asked what, in what order, and why caching makes DNS both fast and occasionally very confusing.

3.1 Stub resolver, recursive resolver, and the four-step lookup

Your OS has a tiny stub resolver that doesn't know how to find anything itself — it just forwards the question to a recursive resolver (your ISP's, or a public one like 1.1.1.1 or 8.8.8.8). The recursive resolver does the real work, walking down the DNS hierarchy:

  1. Ask a root server: "who handles .com?" → gets pointed to the .com TLD servers.
  2. Ask a TLD server: "who handles example.com?" → gets pointed to example.com's authoritative nameservers.
  3. Ask the authoritative nameserver: "what's the A record for example.com?" → gets the actual IP address.
  4. Return that answer to your device, and cache it for next time.
SEO angle: Googlebot uses Google's own recursive resolvers, which have their own cache. A DNS change you just made might already be live for you (fresh local cache) while Googlebot is still serving a cached, stale answer from before — this is the single most common cause of "I fixed it, why does Search Console still show the old error?"
  • Believing "DNS propagation" is one global event; it's actually thousands of independent caches expiring on their own schedule.

3.2 Caching, TTL, and what happens when DNS fails

Every DNS record has a TTL (time-to-live) in seconds — how long a resolver is allowed to cache the answer before asking again. A low TTL (e.g. 300s) means changes spread faster but you generate more lookup traffic; a high TTL (e.g. 86400s) means faster repeat lookups but slower rollout of changes.

If DNS fails — a nameserver is unreachable, a record was deleted, TTL expired mid-migration — the browser (or crawler) simply cannot find an IP address to connect to, and the request never even reaches step 3 of the journey. This is the earliest possible point of total failure, and it produces a DNS_PROBE_FINISHED_NXDOMAIN-style error, not an HTTP error, because no HTTP request was ever sent.

SEO angle: before any planned DNS change (migration, provider switch), lower the TTL of the records you're about to touch a day or two in advance. That shrinks the stale-cache window for every resolver, Googlebot's included.

The stub resolver (on your device) can't resolve anything itself — it forwards the question to a recursive resolver, which does the actual walk through root → TLD → authoritative servers.
Check question 2 — Why can two people see different results right after a DNS change?

Day 4 3 h

DNS records and SEO setup

DNS isn't just "the A record." Today you learn every record type you'll actually meet as an SEO, and the www-vs-apex decision that trips up nearly every migration.

4.1 Record types you'll actually use

  • A — maps a name to an IPv4 address.
  • AAAA — maps a name to an IPv6 address.
  • CNAME — points one name to another name (not directly to an IP). Can't coexist with other records on the same name — a common source of conflicts at the root/apex.
  • NS — declares which nameservers are authoritative for the domain (or a subdomain).
  • MX — where email for the domain should be delivered. Unrelated to the website, but frequently broken by accident during "web" migrations.
  • TXT — free-text data used for verification (Google Search Console site ownership, SPF/DKIM for email authentication) and other machine-readable metadata.
  • CAA — restricts which certificate authorities are allowed to issue TLS certificates for the domain, a security control you'll meet again on Day 5.
SEO angle: a TXT record is very likely how you verified your domain in Search Console. If a domain migration wipes and replaces all DNS records without preserving that TXT record (and any others like SPF/DKIM), you silently lose Search Console verification and break company email deliverability in the same move.
  • Deleting "unused-looking" TXT or MX records during a DNS cleanup without checking what depends on them first.

4.2 www vs. apex, subdomains, and migrations

The apex (or "root," or "naked") domain is example.com with nothing in front. www.example.com is technically a subdomain, historically used to separate "the website" from other services on the bare domain (mail, ftp). Modern practice is to pick one as canonical and 301-redirect the other permanently — Google treats www and non-www as different URLs unless you tell it otherwise.

Technically, the apex has historically been unable to use a CNAME (it must use A/AAAA records, since the apex also needs to hold NS and other records) — many providers now offer "CNAME flattening" or "ALIAS" records to work around this at the DNS layer.

SEO angle: pick www or non-www once, redirect consistently everywhere (DNS, server config, canonical tags, internal links, sitemap), and never let both versions serve 200 OK with real content — that's duplicate content Google has to reconcile, and signals get split between the two.

Day 5 3 h

TCP, TLS, servers and CDNs

DNS gave you an IP address. Today you learn what happens once the browser actually connects to it — and who, in practice, is on the other end.

5.1 The TCP handshake

Before any data flows, client and server perform a three-way handshake: SYN (client: "can we talk?") → SYN-ACK (server: "yes, go ahead") → ACK (client: "confirmed"). This establishes a reliable, ordered connection — the foundation HTTP is built on. Each leg of that handshake costs at least one network round trip, and on a slow or distant connection this adds real, measurable latency before a single byte of your page has been requested.

SEO angle: this is why being physically closer to your users (or using a CDN with edge nodes near them) cuts load time even before your server does any work — you're cutting round-trip time on the handshake itself, not just download speed.

5.2 TLS and certificates

For HTTPS, right after (or, with TLS 1.3, nearly overlapping) the TCP handshake, client and server negotiate encryption: agree on a cipher, the server presents its certificate (proving it really is example.com, signed by a trusted certificate authority), and both sides derive session keys. Only after this is the actual HTTP request sent, encrypted.

A CAA DNS record (Day 4) restricts which certificate authorities are even allowed to issue a cert for your domain — a defense against a misissued certificate from an unrelated CA.

SEO angle: HTTPS has been a confirmed, if lightweight, Google ranking signal for years, and browsers actively warn users off HTTP pages — so a broken, expired or misconfigured certificate doesn't just fail silently, it actively scares visitors away and can affect how Google treats the page.
  • Letting a certificate expire unnoticed because renewal isn't automated or monitored.

5.3 Web servers, hosting, reverse proxies and CDNs

The origin server runs the actual application (WordPress, a static site, a custom app) behind web server software like Nginx or Apache. Between the internet and the origin, a reverse proxy (often the same Nginx, or a dedicated tool) can handle TLS termination, caching, load balancing across multiple origin servers, or routing.

A CDN (content delivery network) is a network of servers ("edge nodes") in many locations that cache and serve your content close to each visitor, so most requests never even reach your origin server. This is why the "IP address" you look up for a big site is often a CDN edge IP, not the origin's real IP.

SEO angle: a misconfigured CDN cache can serve Googlebot a stale version of a page — old title tags, old content, even an old noindex — long after you've published a fix, because the crawler is hitting the edge cache, not your live origin.

7.1 How Googlebot experiences the journey

Googlebot follows the exact same journey you've studied all week: DNS resolution, TCP connect, TLS, request, response — using Google's own infrastructure and resolvers, which is why its cache timing can differ from yours. Google adjusts its crawl rate based on how your server responds: consistent errors, timeouts, or slow responses cause Google to crawl more cautiously (and less), which can slow down discovery and re-indexing of new or updated content.

This whole plan stops exactly where the server starts to answer — everything from here (status codes, headers, HTML, rendering, JavaScript execution) is a separate stage that determines what Googlebot does with the response, not whether it can get one at all.

SEO angle: "crawl budget" problems are frequently blamed on content structure when the real bottleneck is server response time or DNS reliability — this week's whole toolkit (dig, curl timing, DevTools) is how you tell the difference before proposing a fix.

7.2 TTFB in context

TTFB (Time to First Byte) is the gap between the request being sent and the first byte of the response arriving — it wraps up everything from Day 5's TCP/TLS handshakes through however long your server (or CDN cache) took to generate or fetch the response. It's a diagnostic number, not itself a Core Web Vital, but a high TTFB makes it much harder to hit good Largest Contentful Paint scores, because nothing on the page can render before the first byte lands.

Cheat sheet — commands and quick reference

nslookup

nslookup example.com                 # A record + resolver used

dig example.com TXT
dig example.com NS
dig example.com +trace               # full root -> TLD -> authoritative chain
dig example.com +short               # just the answer, no extra output
